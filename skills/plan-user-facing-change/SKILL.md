# 写用户视角的变更方案

先从需求、现有行为和已确认的约束中明确谁遇到什么问题，以及改完后希望达成什么。用户提供的用词、数据及责任边界是方案的依据。把现有事实、拟议行为和待决定事项分别写清。

1. 描述改动前后用户能看到的变化。对于后台改动，说明用户会获得什么结果、多久能看到，或需要做什么。
2. 从触发动作开始，写清正常路径、与本次变更有关的异常分支，以及哪些步骤由谁执行。需要时补充权限、旧数据和上线阶段的用户体验。
3. 为关键行为给出可观察的验收场景。例如用户取消尚未开始的导出后，清单显示已取消，刷新后状态仍保持。
4. 将真正影响用户体验的取舍留在待确认项中，写明可选行为和各自影响。

交付可供产品和开发共同确认的简短方案。使用读者熟悉的业务词，保留需要据此验收的数字、时机和条件。
