# 设计测试策略

先用需求、改动和现有测试确定要保护的行为。为每项验收标准写出触发步骤和可观察结果，重点覆盖失败、中断、重复执行及兼容路径中与本次改动相关的部分。

1. 为每个风险选能提供足够证据的最小测试层。规则判断可用单测，组件交互和持久化用集成测试，公开接口用契约测试，跨界面的关键用户路径用端到端测试。
2. 明确每项测试用到的外部依赖、身份、环境、测试数据和写入副作用。依赖行为属于被验证内容时，使用受控的真实组件或隔离环境。只需要控制时间、随机性或远端故障时，优先使用已有的可控边界。
3. 将快速、可重复、独立的检查放进常规 CI。为依赖共享环境的检查说明清理及隔离方式。会写生产数据、发送通知或产生费用的场景应有独立运行入口，明确执行人及授权条件。
4. 对慢或不稳定的场景，先定位等待、共享状态或环境依赖。用可控时钟、确定性同步或最小数据集缩小耗时，保留原来要验证的行为和断言。

输出验收点、测试场景、预期结果、测试层及执行位置的对应关系。指出现有覆盖、需要新增的验证和只能人工确认的项目。
