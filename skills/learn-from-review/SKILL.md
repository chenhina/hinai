# 从评审中学习

选择一条具体的评审意见，结合对应版本的代码、调用方或现有测试，确认它指出的问题确实成立。分别判断问题是否成立，以及评审者建议的修法是否合适。证据不足时，先记录待核实的问题。

1. 找出让问题可见的信号，例如返回值顺序变了、配置默认值变了，或注释承诺与调用方实际行为有差异。
2. 根据证据重建一条可复用的检视路径。例如修改列表排序后，查依赖首元素的调用方，再核对空列表、并列值和默认排序。评审者实际用了什么方法未知时，把这条路径标成建议。
3. 说明上次遗漏的原因，并把检视方法写成下次能执行的动作。若同类缺陷适合自动验证，补充测试输入、预期结果和通过条件。

默认用短卡片交付，包含问题与证据、发现信号、检视方法、下次动作。用户要求入库时，沿用现有案例位置，也可把方法写入 `notes/`，把可重复验证的场景写入 `evals/`。面向公开仓库时使用去标识的案例。
