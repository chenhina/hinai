# 解决 PR 合并冲突

1. 核对 PR 的 base 仓库、分支和 head 仓库、分支及提交。fork PR 的推送目标取自 head 仓库。检查工作区是否已有合并、变基或用户改动，必要时为此次操作使用单独的 worktree。
2. 获取 base 与 head 的当前快照。从经核实的 head 开始，按用户或仓库约定采用 merge 或 rebase。没有明确约定时优先 merge，保留已有提交历史。
3. 结合共同祖先和两侧变更处理每个冲突，核对相关提交、调用方及测试。区分文本重叠和语义冲突，例如两侧分别改变接口签名与调用逻辑。按仓库约定重新生成锁文件或其他生成文件。若双方的行为要求确实冲突，明确需要用户决定的取舍。
4. 检查未合并条目及引入的冲突标记，复核最终差异，并运行覆盖两侧行为的针对性测试。仅当本地结果完整且用户要求推送时，核对远端 head 是否仍是本次操作的起点，再推到 PR 的实际 head 分支。改写已发布历史需要用户明确授权。

报告处理了哪些冲突、保留了哪些行为、测试结果和远端更新状态。
